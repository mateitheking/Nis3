# Контракты источников

Живой справочник по чужим API. Каждый раздел описывает, что источник отдаёт **на самом деле**,
а не что о нём написано в документации (её нет). Фикстуры реальных ответов лежат в
`tests/fixtures/`, контрактные тесты гоняются против них.

Правило: если источник изменился и тест упал — сначала обновляем этот файл, потом код.

## aSc / EduPage — публичное расписание

**Статус: реализовано и проверено вживую** (`apps/api/sources/asc.py`, 7 сентября 2026).
Авторизация не нужна.

### Эндпоинты

Оба — `POST`, тело `{"__args": [...], "__gsh": "00000000"}`, ответ `application/json`.

| Что | URL |
|---|---|
| Список опубликованных расписаний | `https://{school}.edupage.org/timetable/server/ttviewer.js?__func=getTTViewerData` |
| Таблицы одного расписания | `https://{school}.edupage.org/timetable/server/regulartt.js?__func=regularttGetData` |

`__gsh` — антифорджери-токен; на публичных данных `"00000000"` принимается.

### getTTViewerData

Аргументы: `[null, year]`. **`year` обязателен** — при `null` или отсутствии сервер отвечает
собственным конвертом ошибки `{"e": "Error: 9906805036", "em": "undefined"}` (HTTP 200!).
Год — учебный: расписание на 2026-2027 имеет `year == 2026`, то есть считается от августа.

```json
{"r": {"regular": {
  "default_num": "245",
  "timetables": [{"tt_num": "245", "year": 2026,
                  "text": "расписание на 1 четверть 2026-2027 уч.год",
                  "datefrom": "2026-08-01", "hidden": false}]}}}
```

`default_num` — **указание сервера, какое расписание текущее**. Берём его, а не первый элемент
списка. Он зависит от запрошенного года: при `year=2025` тот же список приходит с пустым
`default_num`. Если пуст — запасное правило: среди не-`hidden` берём максимальный `datefrom`.

### regularttGetData

Аргументы: `[null, "<tt_num>"]`. Ответ — `r.dbiAccessorRes.tables`, список таблиц вида
`{"id": "<имя>", "data_rows": [...]}`.

Таблицы у НИШ Караганда, расписание 245 (для масштаба): `periods:10`, `breaks:3`, `bells:50`,
`daysdefs:7`, `days:5`, `classrooms:70`, `classes:54`, `subjects:89`, `teachers:128`,
`groups:270`, `divisions:162`, `lessons:1106`, `cards:1287`, `students:0`.

Используемые поля (все всегда присутствуют, проверено по всем строкам):

| Таблица | Поля |
|---|---|
| `periods` | `id`, `period`, `starttime` `"08:30"`, `endtime`, `name` |
| `days` | `id` `"0"`..`"4"`, `name`, `short` |
| `classes` | `id`, `name` `"10A"`, `short` |
| `subjects` | `id`, `name`, `short` |
| `teachers` | `id`, `short` — **полного имени нет**, только короткое |
| `classrooms` | `id`, `name`, `short` |
| `lessons` | `id`, `subjectid`, `teacherids[]`, `classids[]`, `groupids[]`, `durationperiods` |
| `cards` | `id`, `lessonid`, `period`, `days`, `classroomids[]` |

`cards.days` — битовая маска по дням, `"01000"` = вторник. Во всех 1287 карточках ровно один
бит. Мы это проверяем и падаем, если не так.

### Две ловушки, на которых легко молча ошибиться

**1. Смешанные id-пространства.** В `classes` 17 записей с id вида `*N` и 37 с `-N`
(`*` — созданные в aSc, `-` — синхронизированные из EduPage). `lessons.classids` ссылается на
оба вида. Сравнивать по формату id или предполагать один префикс — ошибка. Проверено: множества
совпадают ровно, сироток нет ни в одну сторону.

**2. Время урока может быть конвертом, а не временем.** У НИШ Караганда периоды 5 и 6
опубликованы так:

```
period 5: starttime=11:40 endtime=12:50
          name="5 (11.40-12.20) 9-12кл; (12.10-12.50) -7,8 кл"
period 6: starttime=12:25 endtime=13:40
          name="6 (12.25-13.05) -10,11кл; (13.00-13.40) - 7,8,9,12кл"
```

То есть **у одного номера урока разное время для разных параллелей**, а в `starttime`/`endtime`
лежит общий конверт — из-за чего периоды 5 и 6 формально перекрываются. Точное время школа
записала человеческим текстом в `name`; машинно его не достать, формат произвольный. Таблица
`bells` (50 строк) пуста — `perioddata: {}` у всех, и все классы на звонке `"0"`, так что
штатного механизма aSc здесь не использовали.

Что делаем: адаптер находит перекрывающиеся периоды и помечает такие уроки `time_exact=False`,
пронося `period_name` дальше. Показывать это время как точное нельзя — соврём ученику на полчаса.
Для 10A так помечено 6 уроков из 25.

**3. Классное расписание в старших классах — это меню, а не расписание.** У Петропавловска
в 11A за неделю 59 записей, и многие стоят одновременно: в понедельник на 1-м уроке разом
Chemistry, Biology и Informatics, на 5-м — Mathematics в четырёх кабинетах с четырьмя учителями.
Это деления на группы (`groupids`, `divisions`): предметы по выбору, и публичное расписание
показывает все варианты сразу. Реальных уроков у конкретного ученика примерно вдвое меньше.

Сузить до ученика можно только зная его группы, а они доступны лишь после авторизации.
Отсюда: **публичный источник — обзор по классу, личное расписание берём с профиля**
(и в младших классах, где делений нет, разница невелика).

### Покрытие школ

Публикуют расписание не все, и по-разному. Проверено:

| Школа | Результат |
|---|---|
| `nispetropavlovsk` | 83 расписания в истории, `default_num=145`, 46 классов, 1211 карточек |
| `niskaraganda` | одно актуальное, «1 четверть 2026-2027», `tt_num=245`, 54 класса |
| `phmnisastana` | только 2022 год, `hidden=true` — публичного расписания нет |

Перед тем как опираться на публичный источник для конкретной школы, надо проверить её отдельно.

**Почему `default_num` обязателен, а эвристики недостаточно.** У Петропавловска не скрытых
расписаний два — `144` («1 term») и `145` («1 term 0.2»), **и у обоих одинаковый
`datefrom = 2026-09-01`**. Выбор «самое свежее по дате» здесь неоднозначен и с равной
вероятностью дал бы устаревшую редакцию. Сервер указывает `145` явно. Правило «спрашиваем
источник, а не угадываем» — не абстрактное, оно решает конкретно этот случай.

## СУШ — `sms.{school}.nis.edu.kz`

**Статус: разобрано по HAR и ПОДТВЕРЖДЕНО живым входом** (Петропавловск, `sms.ptr`,
7 сентября 2026). Клиент `apps/api/sources/sush.py` вживую логинится, тянет табель за текущий
и прошлые годы, данные совпадают с фикстурами. Флоу **изменился** относительно enis2.
Проверка: `scripts/sush_check.py` (пароль — через `$env:SUSH_PASSWORD`, getpass в терминале не работает).

Версия: СУШ `3.0.289`, ExtJS `7.6.0.41`, ASP.NET MVC. Маршруты `/{area}/{controller}/{action}`.

### Вход

`POST /root/Account/LogOn`, форма: `login` (ИИН), `password`, `twoFactorAuthCode`, `captchaInput`,
`application2FACode`. Сессия — в куках. **На реальном аккаунте капча и 2FA не потребовались**
(`captchaInput` и оба 2FA-поля пустые, вход прошёл). Это хорошо для фоновой синхронизации, но
проверено на одном аккаунте и один раз — не гарантия.

### Капча включается после неудачных попыток — подтверждено вживую

Живой тест 7 сентября: несколько неудачных логинов подряд (из-за бага ввода пароля, не из-за
неверных данных) **включили Google reCAPTCHA** (`captchaType == 2`). Это ровно риск из плана,
и он наблюдаем. Практические следствия для фоновой синхронизации:

* **Никогда не перебирать пароль.** Один неудачный вход — стоп, `CaptchaRequired`, флаг «нужен
  ручной вход». Клиент так и делает (не ретраит).
* Сбрасывается капча **успешным входом через браузер** (решить reCAPTCHA руками — счётчик
  неудач обнуляется).
* Значит фоновый вход надёжен, только пока пароль точно верен и сессия переиспользуется.
  Хранить и жечь логины пачкой — прямой путь под капчу.
* User-Agent обязателен: без браузерного UA сервер отвечает `«Security error»` ещё до
  проверки пароля (enis2 не зря держал FAKE_USER_AGENT).

### Формат ответа (одинаковый у всех data-эндпоинтов)

```json
{"success": true, "state": 0, "data": [...],
 "message": "", "details": null, "code": null, "closable": null,
 "refreshPage": null, "title": null, "duration": null, "total": null}
```

Ошибка приходит с `success:false` и текстом в `message` (например «Нет утвержденной нагрузки на
данную четверть!»). Истёкшая сессия — `«Сессия пользователя была завершена…»`.

**СУШ не даёт параллельных сессий одного аккаунта — живой прогон 14 сентября 2026.** Реальный
вход в СУШ с обычного браузера ученика (просто открыть сайт, ничего не менять) обрывает нашу
фоновую сессию с текстом `«Текущая сессия завершена по причине входа с другой рабочей станции»`.
Это ЧЕТВЁРТЫЙ вариант сообщения об истёкшей сессии, раньше не входивший в
`_SESSION_EXPIRED_MARKERS` — без него `_envelope()` классифицировал ответ как обычный
`SourceError`, а `_session_alive()` (см. `SushClient.has_session()`) отдельно ловит `SourceError`
и трактует его как «сессия жива, просто форма ответа другая» (осознанный компромисс — не путать
дрейф контракта с истечением сессии). Итог: `get_sush_client()` не перелогинивался и отдавал
клиента с мёртвой сессией — на фронте это выглядело как «СУШ не привязан», хотя привязка была в
полном порядке. Добавлено в маркеры, регрессия закрыта тестом.

### Текущий флоу (что изменилось с enis2)

Раньше цепочка шла через `/reportcard/*`. Сейчас — через справочники `/Ref/*` и `/JceDiary/*`,
и **все объекты адресуются GUID-ами**, а не позицией. Порядок:

1. `POST /Ref/GetSchoolYears` — все учебные годы. Тело: `page/start/limit`. Каждый год:
   `{Name, Data:{IsActual, BeginDate, EndDate}, Id:GUID}`. **Текущий помечен `IsActual:true`** —
   берём по нему, а не по позиции. В фикстуре годы с 2023 по 2026 → **история оценок доступна**
   сменой `schoolYearId`.
2. `POST /Ref/GetPeriods` (`schoolYearId`) — четверти. **Приходят в обратном порядке: 4, 3, 2, 1.**
   Это ровно то, на чём упал enis2 (issue #34): `data[0]` даёт 4-ю четверть вместо 1-й. Выбираем
   по `Name`, не по индексу.
3. Цепочка выбора (у ученика в каждом списке ровно один элемент, но адресуемся явно):
   `POST /JceDiary/GetParallels` (`periodId`) → параллель;
   `POST /JceDiary/GetKlasses` (`periodId,parallelId`) → класс (несёт `OrganizationId`, `LetterName`);
   `POST /JceDiary/GetStudents` (`periodId,klassId`) → ученик;
   `POST /JceDiary/GetJceDiary` (`periodId,parallelId,klassId,studentId`) → URL внутреннего
   приложения дневника (или ошибка «нет нагрузки», если четверть пустая).

### Оценки — `POST /Jce/Diary/GetSubjects` (внутреннее приложение дневника)

**`GetSubjects` вхолодную не работает — нужно сперва открыть дневник.** Реальный баг,
пойманный на живом прогоне 8 сентября: первая версия `SushClient.subjects()` стучалась в
`GetSubjects` сразу после логина и падала необработанным 500 (эндпоинт отвечал бизнес-ошибкой
«Нет утвержденной нагрузки», а код это не ловил). Причина — та же цепочка выбора, что и у
дневника (см. выше), плюс ещё один шаг:

```
POST /Ref/GetSchoolYears                                          → учебный год (IsActual)
POST /Ref/GetPeriods            {schoolYearId}                    → четверть (по имени, не data[0]!)
POST /JceDiary/GetParallels     {periodId}                        → параллель
POST /JceDiary/GetKlasses       {periodId, parallelId}             → класс
POST /JceDiary/GetStudents      {periodId, klassId}                → ученик
POST /JceDiary/GetJceDiary      {periodId, parallelId,
                                  klassId, studentId}               → {"Url": "https://.../jce/Diary/Index?..."}
GET  <тот самый Url>                                                → ставит сессию внутреннего дневника
POST /Jce/Diary/GetSubjects     {page:1, start:0, limit:100}       → наконец оценки
```

**GetJceDiary** отдаёт `data.Url` — ссылку на внутреннее приложение (`/jce/Diary/Index?
shId=...&qId=...&studId=...`), или бизнес-ошибку `«Нет утвержденной нагрузки на данную
четверть!»`, если в четверти ещё нет утверждённой нагрузки (пустая/будущая четверть — это не
баг, это честное состояние). Переход по `Url` — **обычный `GET` без тела**, сверено по HAR:
на этом месте я сначала угадал `POST` (по аналогии с `report_card`, где похожий шаг тоже есть,
но устроен иначе) — угадал неверно, поправил по реальному запросу браузера. Аналогия между
двумя подсистемами верна на уровне приёма («открыть внутреннее приложение перед тем, как с
ним работать»), но не на уровне деталей — это две разные системы СУШ (`reportcard` и
`JceDiary`), совпадение архитектуры не значит совпадение метода запроса.

**У СУШ нет признака «текущая четверть».** `/Ref/GetPeriods` отдаёт голые `{Id, Name}`, без дат
и без флага (в отличие от `SchoolYear.IsActual`). `SushClient.subjects(quarter=1)` — четверть
всегда явный параметр, дефолт `1` не как «угадка по календарю», а как честно
задокументированное значение по умолчанию. Гадать по месяцу означало бы рисковать молча
показать не ту четверть как «текущую» — ровно то, чего весь этот проект избегает.

**Главный эндпоинт**, после того как дневник открыт. Отдаёт все предметы четверти одним
ответом, `data` — список из 16:

```json
{"Name": "Английский язык", "JournalId": GUID, "Id": GUID,
 "Score": 66.67, "Mark": 4, "MarkComment": null,
 "Evaluations": [
   {"Type": 2, "ShortName": "СОР", "Name": "Суммативное оценивание за раздел",
    "Percent": 100.0, "MaxScores": {"<assessmentId>": 6.0, ...}, "Id": GUID},
   {"Type": 3, "ShortName": "СОЧ", "Name": "Суммативное оценивание за четверть",
    "Percent": 0.0, "MaxScores": {}, "Id": GUID}]}
```

* `Score` — процент за четверть (0–100), `Mark` — итоговая оценка 1–5.
* **`Percent` — вес вида оценивания, и он приходит из API.** Значит формулу НИШ (СОР/СОЧ)
  искать в положении **не нужно** — сервер отдаёт веса сам, причём они разные по предметам:
  большинство `СОР 50 / СОЧ 50`, а язык и физкультура `СОР 100 / СОЧ 0`. Это снимает
  отдельную задачу Фазы 0 про формулу.
* `MaxScores` — максимальный балл каждого запланированного оценивания (по `assessmentId`).
  Число ключей = сколько СОР/СОЧ в четверти.

**Чего в этом ответе нет:** заработанных учеником баллов по каждому оцениванию — только
агрегат `Score` и максимумы. Поштучные баллы — отдельный эндпоинт, `GetResultByEvalution`,
см. ниже.

**Ловушка, пойманная на живом прогоне 14 сентября: `Id` и `JournalId` предмета — не
стабильные ключи, а идентификаторы сессии внутреннего дневника.** Оба поля из примера выше
выглядят как обычные GUID предмета, и первая версия `/api/grades/subject` адресовалась
именно по `JournalId`, сохранённому в списке `/api/grades`. На реальном аккаунте это
сломалось: `subjects()` заново проходит всю цепочку выбора (см. начало раздела), включая
`GetJceDiary`/открытие внутреннего дневника — а это открывает НОВУЮ сессию дневника при
каждом вызове, и `Id`/`JournalId` каждого предмета — GUID именно этой сессии, не предмета.
Два независимых запроса `subjects()` с одним и тем же живым куки-кэшем (проверено скриптом,
без пароля — расшифровкой уже сохранённой сессии server-side) отдают РАЗНЫЕ `JournalId` для
одного и того же предмета:

```
запрос A: Английский язык → JournalId f2e12132-...
запрос B: Английский язык → JournalId 34e4ecc2-...   (тот же аккаунт, те же куки)
```

Раз `/api/grades` (список) и `/api/grades/subject` (детали по клику) — два отдельных HTTP-
запроса, каждый со своим вызовом `subjects()`, `journal_id`, пойманный в первом запросе,
почти гарантированно не находится во втором → 404 → фронтенд тихо показывал «Не
запланировано в этой четверти» вместо реальных тем (хотя `Score`/`Mark` уже посчитаны и
видны — они не зависят от этой цепочки). Исправлено адресацией по `Name` предмета — оно
единственное стабильно между запросами (и уникально: 16 разных предметов в четверти).
`Id`/`JournalId` остаются в ответе только для отображения/отладки, не как ключ.

### Табель — `/reportcard/*` + `POST /ReportCardByStudent/GetData`

**Отдельная от дневника подсистема, и она НЕ менялась с enis2.** Схема ответа совпадает с
enis2 один в один. Цепочка выбора (все параметры — GUID/имена, `roleId=Ученик`):
`GetOrganizations` → `GetParallels` → `GetKlasses` → `GetStudents` → `GetUrl` (даёт URL
внутреннего отчёта) → `ReportCardByStudent/GetData`. Годы переключаются `schoolYearId` —
проверено на 2024-2025, 2025-2026.

Каждая строка `GetData` — предмет с оценками за все периоды:
`FirstPeriod`..`ForthPeriod`, `FirstHalfYear`, `SecondHalfYear`, `Year`, `Exam`, `Final`.
Фильтр как в enis2: `IsNotChosen == true` и `ComponentName == "Инвариантный компонент"` (12 из 16;
остальные 4 — вариативный компонент). Плюс `EvaluationSystemName`: «Журнал КО» (числовые 1–5)
и «Традиц. журнал» (зачёт).

**Ловушка: всё приходит строками.** Оценка — `"4"`, зачёт — `"true"`/`"false"`, «не выставлено» —
`"none"` (наравне с настоящим `null`). Без нормализации в интерфейсе появилось бы буквальное
«none». Разбирает `normalize_mark`: число → `int`, `"true"`→«зачёт», `"none"`/`null`→`None`.

### Поштучные баллы — `POST /Jce/Diary/GetResultByEvalution`

`{journalId, evalId}` → список рубрик оценивания с реальными баллами:
`{Name: "Listening", Score: 3.0, MaxScore: 6, RubricId, Id}`. Проверено сквозняком: сумма
рубрик СОР по английскому 16/24 = 66.7% совпадает со `Score` из `GetSubjects` (66.67). Это
закрывает то, чего не хватало калькулятору — заработанные баллы по каждому оцениванию.

### Что теперь есть целиком

* вход (на этом аккаунте без капчи/2FA);
* текущие оценки с весами СОР/СОЧ (`GetSubjects`);
* поштучные баллы (`GetResultByEvalution`);
* табель за все четверти/год (`ReportCardByStudent/GetData`);
* прошлые годы (сменой `schoolYearId`, проверено на 3 годах).

Фаза 0 по СУШ по сути закрыта. Фикстуры — `tests/fixtures/sush/*.json`.

### Прочее в HAR (не наше)

`/Routes/*` — школьные маршруты/транспорт (`route.nis.edu.kz`), не расписание.
`/School/MonitoringReports/Index` — вернул **HTTP 500** (мониторинг СОР, что-то сломано на сервере).

### Доступность школ

18 из 20 отвечают. `sms.fmalm` (Алматы ФМН) и `sms.atr` (Атырау) — таймаут.

## NIS mektep

**Статус: бэкенд найден, схема авторизации не подтверждена.** Интересен способом авторизации:
если токены — отпадает и капча, и хранение чужих паролей.

### Приложение

`kz.edu.nis.mobios`, iOS-версия 2.15.1 (build 253). **Написано на Flutter** — выяснилось из
запроса приложения в AppMetrica (`app_framework=flutter`), пойманного mitmproxy.

**Перехват трафика на iPhone без джейлбрейка не работает.** Не из-за certificate pinning:
Flutter (Dart `dart:io` HttpClient) не использует ни системное хранилище сертификатов, ни
системные настройки прокси. Проверено на живом устройстве: сертификат mitmproxy установлен и
доверен (Sentry и AppMetrica через нативный iOS-стек расшифровались штатно), но запросов
приложения к API в прокси нет вообще — Dart прошёл мимо. Инструмент разведки — в
`docs/capture-mektep.md`, но для Flutter+iOS он тупиковый.

### Бэкенд (через Certificate Transparency)

Хост приложения так и не пойман, но инфраструктуру видно в журналах прозрачности сертификатов
(`crt.sh`, дамп в `captures/crtsh_nis.json`, 203 поддомена `nis.edu.kz`). Кластер микросервисов,
почти наверняка обслуживающий mektep:

| Хост | HTTP на `/` | Назначение по имени |
|---|---|---|
| `identity.micros.nis.edu.kz` | 404 | аутентификация |
| `reportcard.micros.nis.edu.kz` | 404 | табель/оценки |
| `schedule.micros.nis.edu.kz` | **403** | расписание |
| `notify.micros.nis.edu.kz` | 404 | уведомления |
| `contingent.micros.nis.edu.kz` | 200 | контингент |

Все — `nginx/1.18.0 (Ubuntu)` + `X-Powered-By: ASP.NET`. 404 на корень для API нормально (нет
корневого маршрута); 403 у `schedule` — путь есть, нужна авторизация. Отдельный `identity`-сервис
— сильный признак токенной (OAuth/OIDC) авторизации.

**Что закрыто:** публичные discovery-документы не отдаются —
`identity/.well-known/openid-configuration`, `identity/swagger`, `reportcard/swagger/v1` все 404
(нормально для прода). Дальше угадывать пути аутентификации — уже перебор, не делаем без явного
основания.

### Как продвинуться (когда/если вернёмся)

Единственный надёжный путь на iOS — **разобрать сам IPA**: Flutter-сборка несёт базовые URL и
схему авторизации в коде (`libapp.so`, Dart-снапшот) и в ассетах. Достать IPA с
не-джейлбрейкнутого iPhone нетривиально — отдельная задача. До тех пор mektep — гипотеза, а не
источник.

### Отброшенные проверки (чтобы не повторять)

Отдельного «мобильного» хоста у mektep нет: `api.nis.edu.kz`, `mobile.nis.edu.kz`,
`mektep.nis.edu.kz`, `app.nis.edu.kz`, `nismektep.nis.edu.kz`, `sms.nis.edu.kz` **не имеют
A-записи**. Угаданные мобильные маршруты на школьном хосте СУШ (`/Mobile/*`, `/MobileApi/*` и др.)
редиректят — не существуют. Бэкенд оказался в отдельном кластере `*.micros.nis.edu.kz`.

## EduPage авторизованный

**Статус: реализовано и подтверждено живым входом** (`apps/api/sources/edupage.py`,
8 сентября 2026, НИШ Петропавловск). Библиотека `edupage-api` 0.12.5, GPL-3.0 — обёртка,
не HTTP-клиент с нуля (см. обоснование стека). Фикстуры — `tests/fixtures/edupage/`,
живая проверка — `scripts/edupage_client_check.py`.

### issue #95/#81 больше не воспроизводятся

`get_my_timetable()` — тот самый метод с открытыми багами `Insufficient privilege` и
`IndexError` — на живом аккаунте отработал чисто: реальные предметы, учителя, кабинеты,
периоды. Похоже, это и есть тот фикс, что виден в коммитах `29.07.2026 "Add RPC-based
login flow fallback"` и `10.08.2026 "Make RPC login actually complete..."`. Расписание с
профиля ученика — основной путь, как и планировали, публичный aSc остаётся в запасе.

### Слепая зона библиотеки: события классифицируются по внешнему конверту

`TimelineEvent.event_type` — это тип **внешнего конверта**, и у СОР, СОЧ, БЖБ, классного
часа и линейки он всегда один — `EVENT`. Настоящий тип лежит во вложенном
`additional_data["typ"]` и библиотекой не разворачивается:

| `additional_data["typ"]` | Значение | Совпадает с `EventType` |
|---|---|---|
| `bexam` | СОР, СОЧ, БЖБ, тесты (учителя называют по-разному) | `BIG_EXAM` |
| `schoolevent` | Классный час | `SCHOOL_EVENT` |
| `ttcancel` | Линейка / отмена по расписанию | `TT_CANCEL` |
| `representation` | Собрание/встреча (например с советником) | `REPRESENTATION` |

`apps/api/sources/edupage.py::parse_calendar_event` реклассифицирует по этому полю заново.
Названия видов оценивания не унифицированы даже в одной школе — «СОР 1» и «СОР1» от разных
учителей одного класса — показываем как есть, не пытаемся привести к канону.

**Дата события — `additional_data["date"]`, не `TimelineEvent.timestamp`.** `timestamp` —
момент, когда учитель создал запись, а не дата самого события. У `bexam` дублируется в
`dateto` (проверено: совпадают на всех 10 bexam-записях фикстуры). Взять `timestamp` за
дату СОР — прямая ошибка, календарь показывал бы даты создания вместо дат экзаменов.

**Не у каждого `typ=schoolevent` есть `date` — живой прогон 14 сентября 2026.** Раньше
предполагалось (и было закреплено `ContractError`), что дата в `additional_data` есть у
всех calendar-типов без исключения. На реальном аккаунте пользователя пришло настоящее
`schoolevent` (классный час) без поля `date` вообще — не опечатка формата, поле просто
отсутствует. `EdupageClient.calendar_events()` больше не даёт одному такому событию ронять
весь список: ContractError на отдельном событии ловится и печатается предупреждением
(`[edupage] пропускаю событие: ...`), остальные события в ответе остаются. `parse_calendar_event()`
как чистая функция по-прежнему кидает `ContractError` наружу — ловля именно в
`calendar_events()`, не размазана глубже.

**События без разбираемого типа (`event_type is None`) — на практике групповой чат
класса**, с текстом сообщений и настоящими ФИО учеников внутри вложенного объекта
(ключ `meno`). Пропускаются целиком, текст не логируется и не сохраняется — поймано и
исправлено на собственной фикстуре, см. `redact()` в `scripts/edupage_fixtures.py`.

### Сообщения: та же лента, отдельный `typ` — `sprava`

Добавлено 14 сентября 2026 (изначально был осознанный стаб). Источник тех же данных, что
и календарь, — `get_notification_history` — но у сообщений (объявления от учителей/
администрации) внешний `event_type` библиотеки **уже** правильно размечен как `MESSAGE`
(`EventType.MESSAGE = "sprava"`), в отличие от bexam/schoolevent/ttcancel/representation,
у которых он всегда `EVENT` (слепая зона выше). Значит доставать реальный подтип из
`additional_data["typ"]` для сообщений не нужно — `TimelineEvent.event_type.name ==
"MESSAGE"` уже достаточно надёжен, `apps/api/sources/edupage.py::parse_message` фильтрует
именно по нему.

**Не путать с групповым чатом класса.** Тот тоже приходит через `get_notification_history`,
но с `event_type is None` (см. выше) — это отдельная, неразмеченная категория, не `sprava`.
Проверено: множества `event_type is None` и `event_type == MESSAGE` не пересекаются, фильтр
по `MESSAGE` группового чата не подхватывает.

**Библиотека умеет только отправлять, не читать напрямую.** Есть готовый `Messages.
send_message()`, но нет метода вида «получить сообщения» — читаем через тот же
`get_notification_history`, что и календарь, просто с другим фильтром на выходе. Отправку
сознательно не подключали: `send_message()` сырой (открытый issue про пустой `changes`).

**Апдейт 14 сентября: показываем не только `sprava`, а единую ленту «Уведомления».** На
этом аккаунте `sprava`-сообщений за 30 дней оказалось честных 0 — карточка выглядела
сломанной, хотя реальное приложение EduPage под тем же названием (Notifications) показывает
насыщенную ленту: линейки, СОР/СОЧ/БЖБ и отменённые внерасписанные занятия вперемешку,
отсортированные по дате ПУБЛИКАЦИИ, а не события. `EdupageClient.notifications()` — новый
метод, который сливает `parse_calendar_event`/`parse_message` в один список по этому же
принципу, `NotificationItem.posted_at` — как раз тот сорт-ключ. Один нюанс: `since` для
этой ленты идёт в сеть буквально (без трюка с `_HISTORY_LOOKBACK_DAYS` из calendar_events)
— фильтр «дата публикации» здесь ровно то, что понимает сервер, рассинхрона нет.

**Найден и намеренно не показан четвёртый `additional_data["typ"]` — `lesson`.** Внерасписанное
занятие/консультация («Подготовка к ВСО», с флагом `cancelled: true`, приложение EduPage
подписывает такие записи «Консультация»). Тот же факт уже отдаётся отдельным путём —
`get_timetable_changes`/`schedule_changes()`, показывается на Расписании. Показать его ещё
раз в Уведомлениях под другой подписью значило бы дублировать один факт под двумя разными
ярлыками — `notifications()` его сознательно пропускает (не в `_KNOWN_KINDS`, не `sprava`).

### `datefrom` в `get_notification_history` — дата СОЗДАНИЯ записи, не события

Живой баг 14 сентября 2026, пойманный на реальном аккаунте пользователя после того, как
«Ближайшие события» показали пустой список при 13 реальных предстоящих СОР/СОЧ/БЖБ.
`EdupageClient.calendar_events(since)` раньше слал `since` в сеть буквально —
`get_notification_history(datefrom=since)`. Сервер интерпретирует `datefrom` как фильтр по
дате **создания** записи в ленте, не по дате самого события: учитель публикует «СОР1 —
30.09.2026» заранее, ещё 3 сентября, и запись в ленте несёт именно эту (раннюю) дату
создания. Вызов `calendar_events(date.today())` (ровно то, что делает
`/api/events/upcoming`) с `datefrom=14.09` вымел из ответа сервера вообще все записи,
включая те, чьё СОБЫТИЕ ещё впереди — потому что все они были СОЗДАНЫ раньше сегодня.

Проверено сравнением вживую на одной и той же сессии: `get_notification_history(сегодня)`
→ фактически 0 полезных записей; `get_notification_history(30 дней назад)` → 21 сырая
запись, 13 из них — реальные предстоящие СОР/СОЧ/БЖБ с датами 16.09–08.10.2026.

Исправлено разделением двух смыслов: в сеть всегда уходит фиксированный запас назад
(`_HISTORY_LOOKBACK_DAYS = 60`, независимо от `since`), а `since` фильтрует уже
РАЗОБРАННЫЕ события по `event_date` — том самом поле, которое отличается от даты создания
(см. «Дата события» ниже). `messages()` этой проблемы не имеет: у сообщения дата создания
и есть его «дата события», разделять нечего.

### Замены и консультации: `get_timetable_changes` отдаёт всю школу

Библиотечный метод возвращает замены **по всей школе**, не по классу ученика: на 3 дня —
47 записей, 27 разных классов, из них своему классу (12E) принадлежат 2. Без фильтра
календарь ученика был бы завален чужими консультациями.

Два независимых момента:

1. **«Консультация» не входит в `Action` enum библиотеки** (`add`/`change`/`remove`) —
   для таких записей `action` всегда `None`. Различаем по слову в заголовке
   (`_CONSULTATION_RE`), причём источник сам пишет с опечаткой — `«Кнсультация»`
   (без «о») наравне с правильным написанием. Регэксп ловит обе формы.
2. **Общешкольные мероприятия** («Служения общества», «Тәлімгерлік») публикуются под
   псевдо-классом `«Календарь»` со списком затронутых классов текстом внутри заголовка
   (`«Классы: 11A, 11B, ...»`), а не структурированным полем. `matches_class()` ищет имя
   класса **целым словом** в этом тексте — иначе `«1A»` совпало бы внутри `«11A»`.

**Номер урока — три разных смысла в одном поле.** `lesson_n` бывает числом (`8`),
диапазоном номеров (`(7, 8)`) или временем ЧЧММ для внерасписанных консультаций
(`(1530, 1600)`). Различаем по величине: оба числа ≥ 100 — время, иначе номера уроков
(уроков больше ~20 не бывает).

### Баг источника: у `EduStudent.class_id` иногда пропадает знак минуса

Все id классов в справочнике сессии (`edupage.data["dbi"]["classes"]`) — отрицательные
(`-80`, `-94`…). `People(edupage).get_students()[0].class_id` на практике вернул `10`
вместо `-10` — знак потерян при разборе внутри самой библиотеки. `own_class_name()`
пробует id и со знаком, и без, прежде чем сдаться. Есть explicit override
(`EdupageClient(subdomain, own_class="12E")`), если фикс не поможет на другом аккаунте —
не полагаемся на автоопределение как на единственный путь.
